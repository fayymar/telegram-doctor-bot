# Авторизация API (с ноября 2026)

Раньше API доверял `user_id` из URL или тела запроса, поэтому любой мог читать и менять чужие данные.
Теперь бэкенд выдаёт **токен сессии**, и все запросы к данным пользователя идут с заголовком

```
Authorization: Bearer <token>
```

`user_id` берётся только из токена. Если в URL указан чужой `{user_id}`, сервер отвечает `403`, без токена — `401`.

## Как получить токен

| Откуда вход | Запрос | Тело |
|---|---|---|
| Telegram Mini App (symptoMed-app) | `POST /api/auth/telegram-webapp` | `{"init_data": Telegram.WebApp.initData}` |
| Сайт, Telegram Login Widget | `POST /api/auth/telegram-widget` | объект пользователя от виджета (`id, first_name, …, auth_date, hash`) |
| Сайт, Google/email (Supabase Auth) | `POST /api/auth/social` | `{"access_token": session.access_token}` |
| Сайт, код из бота | `POST /api/auth/code` | `{"code": "K7RM-4QXA"}` |

Все способы входа возвращают `{"token", "id", "first_name", ...}`. Токен живёт 30 дней.
Проверить его можно запросом `GET /api/auth/me`.

### Код из бота (вход и привязка Telegram)
Код **выдаёт бот** пользователю в его собственный чат: команда `/login`, кнопка «🌐 Войти на сайт» или ссылка
`t.me/<бот>?start=login`. Пользователь **вводит код на сайте**. Код из 8 символов (буквы и цифры без похожих, регистр не важен, например `K7RM-4QXA`), действует 5 минут, одноразовый,
привязан к Telegram-аккаунту, который его получил.

- Вход: `POST /api/auth/code {"code"}` → токен сессии Telegram-пользователя.
- Привязка Telegram к веб-аккаунту: `POST /api/auth/link {"code"}` с токеном веб-сессии. Пустые поля веб-профиля
  заполняются из Telegram-профиля.

Раньше было наоборот: сайт показывал код, а бот его подтверждал. Это позволяло фишинг. Злоумышленник присылал
жертве ссылку `?start=auth_КОД`, жертва нажимала «Start», и злоумышленник входил в её аккаунт; так же работала
и привязка. Старые ссылки `auth_` и `link_` теперь ничего не делают.

Защита от перебора: около 8.5·10¹¹ вариантов кода и 10 попыток в минуту с одного IP. Общей блокировки нет, чтобы нельзя было специально заблокировать вход всем.

### Что изменилось для `/api/auth/social`
- Email и `provider_id` из тела больше не принимаются. Нужно передавать `access_token` из сессии Supabase.
  Сервер сам проверяет его у Supabase и возвращает `id`; фронтенд его не вычисляет.
- ID веб-аккаунтов теперь начинаются с 100 000 000 000. Старый диапазон 5–10 млрд пересекался с реальными ID Telegram.

## Эндпоинты, которым нужен токен
`/api/profile/*`, `/api/consultations/*`, `/api/medications/*`, `/api/diary/*`,
`/api/health/heartrate/{id}` (GET), `/api/health/metrics/{id}` (GET), `/api/health/metrics/report/{id}`,
`/api/consultation/feedback`, `/api/auth/link`,
`/api/auth/me`, `/api/auth/metrics-token`.

Консультацию (`/api/consultation/*`) можно проходить и **гостем**, без токена.
С токеном учитываются профиль, история и показатели пользователя. Сессию консультации пользователя может продолжить только он сам.
`/api/consultation/result` теперь возвращает `consultation_id`: его нужно передавать в `/feedback`.

## Показатели с Apple Watch / iPhone Shortcut
`POST /api/health/metrics` и `POST /api/health/heartrate` принимают **токен метрик**:
- получить: `GET /api/auth/metrics-token` (с токеном сессии) → `{"token": "..."}`;
- в Shortcut: заголовок `Authorization: Bearer <token>` **или** поле `"token"` в JSON.

Токен метрик действует 180 дней; с ним можно только *отправлять* показатели. Читать данные им нельзя.
Поле `user_id` в теле игнорируется.

## Supabase
Бэкенд должен работать с ключом **service_role**, а на всех таблицах должен быть включён RLS
(см. `migrations/009_enable_rls.sql`, там описан порядок действий). Публичный anon-ключ, который лежит в коде сайта,
после этого не даёт доступа к таблицам.

## Согласие на обработку данных
Данные о здоровье обрабатываются только с согласия пользователя (ст. 25 и 15 закона РУз «О персональных данных»).
Текущая версия текста: `CONSENT_VERSION` в `services/consent.py`. При изменении текста повышайте версию, и все дадут согласие заново.

- `GET /api/consent` (с токеном) → `{"accepted": bool, "version"}`.
- `POST /api/consent {"version", "source": "web"|"miniapp"}` (с токеном) записывает согласие. Устаревшая версия → 409.
- Запись профиля, лекарств, дневника, показателей и привязка Telegram без согласия → `403 {"error": "consent_required"}`.
- Гостевая консультация: `POST /api/consultation/start` должен содержать `"consent_version": "<текущая версия>"`
  (галочка на экране), иначе 403. Факт согласия записывается с id сессии.
- `DELETE /api/account` (с токеном) удаляет все данные пользователя и отзывает согласие.
- В боте: до согласия работают только `/start`, `/help`, `/login`, `/link`, `/privacy`, `/deletedata`, `/cancel`.
  `/deletedata` удаляет данные из всех таблиц, включая согласие.

## Выход и отзыв токенов

Токены подписаны HMAC; сервер дополнительно хранит отозванные токены
(`revoked_tokens`) и момент «выйти везде» для пользователя (`token_cutoffs`),
см. `migrations/012_add_token_revocation.sql`.

- `POST /api/auth/logout` — отзывает токен запроса («Выйти» на этом устройстве).
- `POST /api/auth/logout-all` — отзывает все токены пользователя, включая токен метрик.
- Удаление аккаунта (`DELETE /api/account`, `/deletedata`) отзывает все токены
  удалённых аккаунтов. Mini App после этого сама входит заново по initData.
